# 独立架构与配置

产品分为四层，不再依赖旧插件宿主加载：

```text
Claude Code / Codex / 其他现有 agent 宿主
    ├─ Agent Skill：做什么、如何小步改、怎样看图与验收
    ├─ MCP stdio 适配 ─┐
    └─ CLI 适配 ──────┤
                      ▼
              TypeScript 共享核心
        工具合同 / 输入校验 / 调用 / 错误 / 进程归属
                      ▼
        Blender runtime（Node路由 + Python能力模块）
              ├─ GUI addon → 当前Blender场景
              └─ 持久worker / headless → 独立场景
```

宿主已具备推理循环、会话和权限，本工程不再创建一套通用 agent harness。CLI 与 MCP 共享工具合同与核心，避免两条入口各写一套业务逻辑；Python 继续运行在 Blender 中，使用 bpy/bmesh 和既有的量测、网格、装配、渲染、交付工具。

## 组件职责

| 目录/组件 | 职责 |
|---|---|
| `packages/blender-agent` | 独立可打包的 TS 核心、CLI/MCP 入口及工具 Schema |
| `bridge/runtime` | 复用并维护的实际 Blender 后端与 Python 能力，不负责宿主推理 |
| `bridge/addon` | GUI Blender 主线程执行、视口、选择读取与人工暂停 |
| `skills/blender-agent` | 短入口与按任务加载的 references，独立包原样带入 |
| `scripts/portable-setup.mjs` | 项目级安装/预览/安全卸载；无运行时业务逻辑 |

上游来源、固定版本与复用范围应以仓库溯源记录为准；`.upstream` 只是开发时的只读参考，构建包和消费者不能依赖它。

## 进程与状态

- MCP 采用 stdio，stdout 只承载协议内容，日志写 stderr。相同配置的宿主注册到同一后端；自动后端按活跃客户端计数，首个宿主退出或死亡不清理其他活跃客户端的场景，最后一个客户端离开才清理。显式启动的 persistent 后端在无人连接时仍保留。
- CLI 场景操作先显式 `backend start`，保持相同 port/workdir/Blender 参数、稳定 holder 和 worker 名称，再 call；完成后 `backend stop`。显式停止遇到其他活跃客户端时返回 `BACKEND_IN_USE`，先关闭其他客户端。
- 后端有归属检查；已有非本适配器服务占用端口时拒用，不接管旧服务、不停止别人进程。`workdir` 是本次引擎与产物空间，建议每项目/实例独立。
- GUI 使用用户当前场景，headless/worker 使用独立场景；切换路线要明确加载文件与保存状态。GUI 的未保存改动不会神奇地出现在无头进程中。
- job 的 runId/jobId、worker session、文件快照是不同标识，分别保存。等待超时仅说明客户端没有收到完成结果；状态未知时不自动重试写操作。

## 配置入口

优先使用 CLI 显式参数：

| 参数 | 用途 |
|---|---|
| `--port` | 本适配器后端 HTTP 端口，默认 9877；示例用 19877 避免旧服务冲突 |
| `--addon-port` / `--worker-port` | GUI addon / worker 端口，默认 9876 / 9879；多实例明确隔离 |
| `--workdir` | 本地工作与产物目录，Node 与 Blender 都必须可读写 |
| `--blender` | 实际 Blender 可执行文件；建议生产项目明确指定版本路径 |
| `--timeout-ms` | 调用等待预算；不表示超时后操作一定取消 |
| `--holder` | 本轮 CLI 场景身份；worker操作、lease、写入与release使用同一个稳定值，并行写者使用不同值和worker名 |

`BLENDER_AGENT_HOLDER` 是 `--holder` 的环境变量替代；显式参数优先。MCP 使用当前服务进程的 PID 身份，不需要配置固定 holder。同名 worker 归创建它的 holder 管理；其他 holder 操作返回 `WORKER_OWNED` / HTTP 409，应另用 worker 名，`list/status` 可查询。

CLI 以下调用必须先启动 persistent backend，否则返回 `PERSISTENT_BACKEND_REQUIRED`：do/see/watch；plan 的非 catalog 操作；worker 除 list/status 外的操作；loop 的 target=session；headless；job start；viewport start/restart。其中 do/see/watch、worker 非 list/status、plan 带 session 的非 catalog 操作、loop target=session 还必须显式使用稳定 holder，否则返回 `EXPLICIT_HOLDER_REQUIRED`。lease/release 同样要求显式身份。catalog、doctor 与状态查询仍可独立使用。

复用引擎仍识别以下历史环境变量名，名称是兼容接口，不表示产品依赖旧宿主：

| 变量 | 用途 |
|---|---|
| `DSH_BLENDER_EXE` / `DSH_BLENDER_WORKDIR` | Blender 路径 / 引擎工作目录 |
| `DSH_BLENDER_ADDON_HOST` / `DSH_BLENDER_ADDON_PORT` | GUI addon 地址；默认 127.0.0.1:9876 |
| `DSH_BLENDER_WORKER_PORT` | worker 端口；默认 9879，多实例应分开 |
| `DSH_BLENDER_HOLDER` / `DSH_BLENDER_LEASE_TTL_MS` | 写租约身份/时长；默认 TTL 600000ms |
| `DSH_WORKER_TTL_MS` | 空闲 worker 回收，默认 900000ms；0 关闭回收 |
| `DSH_BLENDER_USER_CONFIG` / `DSH_BLENDER_USER_SCRIPTS` | 无头使用的 Blender 偏好/脚本路径；按调用需求显式启用 |

显式参数在适配器层转为引擎配置；其他引擎设置按环境变量→配置文件→自动探测→默认值解析。不要把一个宿主已有的个人配置隐含传播到团队项目；doctor 回执核对实际生效路径和版本。

MCP 可用配置中的 `env` 设置项目变量；Codex TOML 使用 `[mcp_servers.blender-agent.env]`。不同实例应分别设置后端端口、worker 端口和工作目录；如果连接不同 GUI Blender，addon 面板端口也要区分。

Windows/WSL 混合时，Node 和 Blender 必须看到同一个物理目录。Windows Blender 使用可写 Windows 路径；不要假设 WSL 内部路径或 UNC 可直接写入成功。原生 Linux/macOS 使用自己的绝对路径；核对实际文件存在与可读后再声称交付完成。

## 兼容性边界

通用的是 MCP 协议、工具合同与 Skill 工作方法；宿主的工具权限、上下文长度、图片呈现、模型表现和版本兼容性仍需实际验证。MCP 发现工具不证明模型完成了建模；CLI 自测不证明 Claude/Codex 实际加载了 Skill；无头出图不证明 GUI addon 正常。

本轮已实测 Windows 上 Blender 4.5.15 与 5.0.1 的无头路线，GUI 仅实测 4.5.15。其他操作系统的 CI 尚未运行，不据此宣称跨平台验收通过。

当前工具能力不覆盖写实有机/生物造型、电影级布光/体积/合成、角色绑定；OCR、landmark/人脸、cv2/MediaPipe、DXF、Open3D、manifold3d、glTF-Validator 不应写成默认已安装。开发这些能力需要独立需求与依赖验证，不能借“通用接入”扩大现有能力承诺。
